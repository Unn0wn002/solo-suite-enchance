## Rollback plan

**Precondition**: identify the previous known-good deployment before you need
it — don't discover `wrangler deployments list` for the first time during an
incident.

1. **List recent deployments**:
   ```powershell
   npx.cmd wrangler deployments list
   ```
   This shows deployment IDs and timestamps for the Worker tied to this
   project's Cloudflare account.

2. **Roll back to the last known-good deployment**:
   ```powershell
   npx.cmd wrangler rollback [deployment-id]
   ```
   Omitting `[deployment-id]` rolls back to the immediately preceding
   deployment. Wrangler will prompt for confirmation — confirm only after
   verifying the target ID is actually the last good one, not just the most
   recent.

3. **If the regression is in the OpenAI "Sites" hosting layer rather than the
   underlying Worker** (unconfirmed mechanism, see above): there is currently
   no documented rollback path for that layer in this repository. Escalate to
   whoever manages the Sites project directly rather than assuming
   `wrangler rollback` covers it.

4. **Verify the rollback**: re-run the smoke assertions `tests/rendered-html.test.mjs`
   already encodes (200 response, correct `<title>`, no starter-template
   leftovers) against the live URL, not just locally — a rollback that
   restores old code but not old *config* (e.g. env vars) can still be broken.

5. **Record the incident**: append an entry to `.solo/decisions.md` (what
   broke, what was rolled back to, root cause once known) and update
   `.solo/risks.md` if the incident reveals a new risk class.
